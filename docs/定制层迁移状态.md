# 原版 OpenCode 与 CTF 定制层的区别

## 先说明当前发布缺口

**现有工具箱确实做过定制。但当前 GitHub 预览包没有完整包含这些定制，只发布了上游源码快照、基础配置示例和下载指南。仅下载原版 OpenCode，无法复现作者现在使用的那套环境。**

先发布一个不含定制层的源码/文档包，不能算完成“把现有优化项目打包分享”的目标。这里明确纠正这一发布范围，不将标注 preview 当作交付完成的替代。

## 改动实际在哪里？

根据现有本机启动链和文件核对，定制不是只靠一个 `opencode.exe`：

```text
CTF 入口与运行控制
  ├─ 启动/校验指定 Strata 引擎和同一个本地模型
  ├─ 设置独立配置、缓存、会话及进程资源限制
  └─ 启动 OpenCode CLI，并注入 CTF Agent 配置与本地插件
       ├─ 工具说明、证据与脚本/产物状态
       ├─ 上下文压缩、连续性保留与缓存处理
       └─ 取消、续聊、状态显示及退出清理
```

主要本机文件与职责如下。文件名用于说明迁移范围，不表示它们已经作为可运行代码进入公开仓库。

| 定制内容 | 现有主要文件 | 公开迁移状态 |
| --- | --- | --- |
| 32K/64K 选择、独立环境和生命周期 | `opencode_runtime.py`、`opencode_engine.py` | 未完成 |
| 工作集、加载与运行资源保护 | `opencode_safety.py`、`working_set_guard.py` | 未完成 |
| Windows CLI 进程树限制与所有权清理 | `owned_process_job.py` | 未完成 |
| 精简工具说明、原始线索/证据索引、脚本进度和状态提示 | `ctf-context.mjs`、`ctf-tools.mjs` | 未完成 |
| 64K 压缩及缓存处理 | `ctf-context-64k.mjs`、`ctf-compaction.mjs`、`compaction-cache.mjs` | 未完成 |
| CTF Agent、普通操作权限与受控高风险确认 | 本机 `opencode.json` 与运行时环境 | 公开文件只是简化示例，不等价 |

例如跨午夜自动日期导致前缀缓存失效的处理，是在本地插件中实现的。上游 CLI 不会因为连接同一个模型，就自动拥有这项处理。

这里没有仅凭版本号或文件名宣称本机 CLI 二进制与上游逐字节相同；关键事实是**本机启动器会显式加载上述定制组件，而公开基础连接示例没有加载它们**。

## 为什么下载原版并非足够？

把上游 CLI 作为依赖本身是可行的：它提供 TUI、Agent 循环及插件接口。但最终交付必须是“底座 + 我们的定制层 + 正确的自动加载入口”。

不能让用户下载底座后，就把普通模型聊天或默认工具调用称为同一套优化环境。也不能原样复制本机配置：其中仍有作者的解释器路径、目录布局、插件 URI 和依赖，换一台机器会失败。

## 真正的可运行版至少需要完成什么？

1. 将定制组件迁入公开源码，去除本机路径与私有数据，显式声明依赖和许可。
2. 提供统一入口，定位用户的 CLI、模型及引擎，自动加载正确的 Agent/插件，不要求用户手工照抄作者目录。
3. 保留 32K 默认、64K 显式选择、单模型、取消/停止/退出清理及现有资源保护；不通过放宽保护伪造可用性。
4. 在与原环境隔离的新目录中验证路径含空格/中文、配置加载、工具闭环、缓存行为、压缩、续聊、停止、资源释放及 32K 回退。
5. 将真实验收范围和未通过项写进新版本说明，再提供经过校验的运行包。

是否需要重编译 CLI，应取决于源码/UI改动的实际需求；**不能缺少定制层，也不能把原版底座当成已经完成的优化版。** 当前修订只是说明和发布提示纠正，并未宣称以上迁移已完成。
